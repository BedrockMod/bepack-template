# 发布与故障处理

## 需求

正式链路为校验、frozen 构建、严格扫描、Draft 资产上传、校验后公开 Release。Tag 推送不等于发布成功，工作流跑完也不等于 registry 已收录。

发布必须满足：

- 仅 `v<version>` Tag 触发；Tag 与 `bepack.json.version` 严格一致，`tool-v*` 不得触发作者包发布。
- 使用 frozen build；构建期间不改写版本、lock 或兼容选择。
- 发布资产固定五项，包内 `bepack.json` 与 Release 上的 `bepack.json` 逐字节一致。
- 扫描覆盖最终包、包内全部可执行组件、以及 lock 中非 bundled 的可执行 mod/client 依赖。
- 扫描必须 completed、0 malicious、0 suspicious，且至少一个 harmless/undetected；无凭据、超时、额度不足、空结果均 fail closed。
- 已公开版本不可覆盖；失败不能留下被视为成功的半公开 Release。
- 通知/收录失败不回滚作者 Release，但必须显示“已发布，尚未收录”。

## 架构

### 工作流

| 工作流 | 触发 | 权限 / 职责 |
|---|---|---|
| `pack-check.yml` | PR、main push、手动 | `contents:read`；离线 validate 与工具测试，不接触发布 Secret |
| `pack-release.yml` | `v*` Tag、针对既有 Tag 的手动重试 | 分 job 最小权限；build 无 Secret，scan 仅 VT Secret，publish 仅 `contents:write` |

发布 job 链：

```text
preflight → build → scan → publish → notify
```

- preflight：固定 Tag 和 peel 后的 commit，校验 Tag/版本/仓库/扫描同意，查询既有 Release。
- build：发布 CLI 通过 `node scripts/bepack.mjs build --project DIR --output DIR --frozen --runtime-catalog FILE --runtime-catalog-sha256 HEX` 子进程调用共用工具；可透传 `--generated-at`、`--metadata-dir`、`--staging-dir`。output 目录只允许一个 `<pack-id>-<version>.bepack`，元数据和 staging 不得混入发布输出。 暂存包、外层 manifest、SHA-256 和私有 build-context；不自行打包。
- scan：按 scan-plan 逐项扫描，生成 `scan-report.json`；任一条目不通过则不产出可发布报告。
- publish：组装 `bepack-release.json`，创建或续用 Draft，上传后逐资产校验，全部通过才公开，公开后再复核。
- notify：官方 App/bridge 未配置时明确 skipped；配置后 POST `pack-released` 线索，registry 仍须独立复验。

任务之间用工作流 artifact 传递，publish 绑定同一 run、同一 Tag、同一 commit。按 `(repository_id, tag)` 并发互斥。

### 五项资产

```text
<pack-id>-<version>.bepack
<pack-id>-<version>.bepack.sha256
bepack.json
bepack-release.json
scan-report.json
```

- `.sha256`：UTF-8 无 BOM，单行 `<64hex><两空格><包文件名>\n`。
- `bepack-release.json`：外层声明，含 `schema_version`、`pack_id`、`version`、`version_set`、`mode`、`package_schema_version`、`repository{id,full_name}`、`tag`、`commit`、`generated_at`、`tool{version,sha256}`、`package`、`manifest`、`scan_report`。不含自身哈希/Release ID/下载 URL。
- `scan-report.json`：`schema_version`、`policy="bepack-official-v1"`、`package_sha256`、`completed_at`、`entries[]`；每条含 subject/sha256/size/analysis_id/status/malicious/suspicious/harmless/undetected/analyzed_at。subject 为 `package`、`payload/<路径>` 或 `dependency/<id>/<artifact>`。

### 失败与重试语义

| 场景 | 行为 |
|---|---|
| Tag 与版本不一致 | preflight/build 失败，不创建 Release |
| 缺 VT key / 未同意 | scan 前失败，不创建公开 Release |
| 检出 malicious/suspicious | 不写通过报告，不公开 |
| 分析未完成/超时/服务错误/额度不足 | 失败，不把空结果当干净 |
| build 失败 | 无 Release；保留错误报告 |
| Draft 中断 | 保持私有；同 run 校验摘要后续传 |
| 同版本重试字节不同 | 拒绝复用 Draft，不自动删除、不覆盖 |
| 已公开且五项资产一致 | 返回 `already-published` 幂等结果 |
| 已公开但任一资产/commit/Tag 不一致 | `IMMUTABLE`，拒绝覆盖 |
| 公开后复核失败 | 尝试回退 Draft；回退失败报 `PUBLISH_VERIFY` 并带 Release ID，需人工处理 |
| 通知失败 | 不回滚 Release，显示已发布未收录 |
| Tag 已推但发布失败 | 不自动删 Tag、不强推；不能视为已发布 |

### CLI 与退出码

```text
node scripts/bepack-release.mjs preflight|build|scan|assemble|publish|verify-assets|notify [options]
```

退出码：`0` 成功，`2` 输入/策略失败，`3` 外部服务失败，`1` 内部错误。错误 JSON 输出到 stderr，含 `code`、`message`、`phase`；不得输出 token 或 API key。

`verify-assets` 可独立复验五项资产：

```text
node scripts/bepack-release.mjs verify-assets --assets <dir> --repository-id <id> \
  --tag v1.2.3 --commit <40hex>
```

它只做本地一致性检查，不能替代 registry 从 GitHub API 重新下载和复算。

### 排障顺序

1. 先看失败阶段和稳定错误码；`preflight` 失败多为 Tag/版本、仓库 URL、同意开关或远程查询问题。
2. `build` 失败先确认 catalog 路径与外部可信 SHA-256、lock/组合和元数据是否一致、frozen CLI 是否可用；不要把环境错误当代码错误。
3. `scan` 失败检查 `VT_API_KEY`、`VT_UPLOAD_CONSENT`、账户配额、文件大小、分析状态；超时和未完成不能重试成“通过”。
4. `publish` 失败先查 Draft 是否已存在、是否同字节；不要手工删除或覆盖已公开资产。
5. 公开后复核失败时保留 Release ID 和错误报告，人工确认是否回退 Draft；不要直接强推 Tag。
6. 通知失败只影响收录状态，不撤销 Release；由周期同步或手动补录处理。

### 外部依赖与风险

- runtime catalog 文件及其外部可信 SHA-256 必须同时提供（`BEPACK_RUNTIME_CATALOG_PATH` / `BEPACK_RUNTIME_CATALOG_SHA256` 或对应 CLI 参数）。SHA-256 绑定完整 catalog 原始字节，必须来自维护者审核并固定的独立配置；catalog 自报的 `source.sha256` 仅是上游来源证据，不能代替外部信任根。真实 catalog 提供者尚未落地，测试 fixture 不能用作生产 catalog。
- runtime catalog 是外部兼容事实，不能由发布流水线生成或猜测；模板默认没有该文件。
- 官方 GitHub App 的 webhook 签名校验、delivery 去重、重放防护和 registry dispatch 端点尚未实现/部署；模板只提供客户端契约。
- GitHub 平台级 Release 不可变保护需管理员开启；客户端仍必须逐资产校验摘要。
- VT 上传涉及样本共享和账户配额；作者必须确认自己有权上传作品及依赖。
- Actions pin 到官方 Tag 对应 commit（checkout v4.4.0、setup-node v4.4.0、upload-artifact v4.6.2、download-artifact v4.3.0），但第三方 Action 供应链仍需持续复核。
