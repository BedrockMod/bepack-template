# 作者指南

## 需求

作者维护主清单、版本组合和实际内容，平台路径映射、依赖解析、frozen 打包与发布资产由共用工具和发布流水线处理。作者必须能明确知道：哪些检查已经通过、哪些外部配置尚未完成、失败时 Release 是否可见。

## 架构

四模式为 full、modded、client、mods-only。主清单定义意图，版本组合选择确切版本，发布 lock 由工具生成。
Windows、Android、Linux 是用户平台集合，BDS 是服务器运行时集合；具体目标必须同时区分平台、架构和运行时。
不得仅凭文件扩展名或当前操作系统推断实际兼容性。不得打包游戏本体或安装脚本。

### 发布链路

1. 离线校验：`npm ci --ignore-scripts`、`npm test`、`npm run validate`。这只证明草稿结构和本地引用合法。
2. frozen build：发布 CLI 通过 `node scripts/bepack.mjs build --project DIR --output DIR --frozen --runtime-catalog FILE --runtime-catalog-sha256 HEX` 子进程调用共用工具；可透传 `--generated-at`、`--metadata-dir`、`--staging-dir`。output 目录只允许一个 `<pack-id>-<version>.bepack`，元数据和 staging 不得混入发布输出。 runtime catalog 文件及其外部可信 SHA-256 必须同时提供（`BEPACK_RUNTIME_CATALOG_PATH` / `BEPACK_RUNTIME_CATALOG_SHA256` 或对应 CLI 参数）。SHA-256 绑定完整 catalog 原始字节，必须来自维护者审核并固定的独立配置；catalog 自报的 `source.sha256` 仅是上游来源证据，不能代替外部信任根。真实 catalog 提供者尚未落地，测试 fixture 不能用作生产 catalog。
3. 严格扫描：发布脚本推导 scan-plan，扫描最终包、包内可执行 payload、以及 lock 中非 bundled 的 mod/client 可执行依赖。所有条目必须 `completed`、`malicious=0`、`suspicious=0`，且至少一个引擎为 `harmless`/`undetected`。
4. Draft 与公开：五项资产上传到同一个 Draft，逐项校验大小与 SHA-256 后才公开；同版本已公开且摘要不同会被拒绝。
5. 收录：官方 GitHub App/bridge 接收 Release 事件后由 registry 独立复验。发布成功不等于已收录；未配置通知时显示“已发布，尚未收录”，不撤销作者 Release。

发布资产固定为 `.bepack`、同名 `.sha256`、`bepack.json`、`bepack-release.json`、`scan-report.json`。`bepack.json` 必须与包内投影字节一致，不能上传未裁剪工程主清单。

## 备注

### 本地检查

已提供 [离线校验工具](../tools/bepack-tool/README.md)：Node.js 22+ 下执行 `npm ci --ignore-scripts`、`npm test`、`npm run validate`。会自动读取激活版本组合，无需生成 lock。所有错误均有 file / JSON Pointer 定位。

离线校验不解析远程元数据或推导真实兼容。空工程通过仅代表草稿结构合法，不能发布；缺兼容信息必须在解析/发布阶段报错，不能解释为全版本兼容。

### 发布前必须配置

| 配置 | 值 / 位置 | 说明 |
|---|---|---|
| 包 ID 与版本 | `bepack.json` | 包 ID 不能再用 `example.my-pack`；Tag 必须是 `v` + `version` |
| 作者仓库 | `bepack.json.repository` | HTTPS GitHub 仓库 URL；不能含 token |
| `VT_API_KEY` | 仓库 Secret | 只给 scan job；缺失时发布失败 |
| `VT_UPLOAD_CONSENT` | 仓库 Variable，值必须为 `true` | 明确同意上传最终包及可扫描的可执行依赖；不是自动许可判断 |
| runtime catalog / 依赖元数据 | 真实来源 | 不允许伪造兼容数据；当前模板没有内置 catalog |
| `BEPACK_RUNTIME_CATALOG_PATH` | 仓库 Variable，指向已 pin 的 catalog 文件 | build 只读取该文件；未设置或文件缺失时失败关闭 |
| `BEPACK_RUNTIME_CATALOG_SHA256` | 仓库 Variable，64 位小写十六进制 | 必须是维护者审核后的完整 catalog 文件摘要，不可只信任文件内部摘要 |

**这些外部 Secrets/App 尚未在模板仓库配置。** 在配置完成前不要推正式 Tag。官方 GitHub App、bridge 服务和 registry dispatch 端点也尚未部署；模板中的 notify 只在配置了 `BEPACK_REGISTRY_DISPATCH_URL` 和 token 时尝试 dispatch，否则明确 skipped。

### 当前限制

- 发布 CLI 通过 `node scripts/bepack.mjs build --project DIR --output DIR --frozen --runtime-catalog FILE --runtime-catalog-sha256 HEX` 子进程调用共用工具；可透传 `--generated-at`、`--metadata-dir`、`--staging-dir`。output 目录只允许一个 `<pack-id>-<version>.bepack`，元数据和 staging 不得混入发布输出。
- runtime catalog 文件及其外部可信 SHA-256 必须同时提供（`BEPACK_RUNTIME_CATALOG_PATH` / `BEPACK_RUNTIME_CATALOG_SHA256` 或对应 CLI 参数）。SHA-256 绑定完整 catalog 原始字节，必须来自维护者审核并固定的独立配置；catalog 自报的 `source.sha256` 仅是上游来源证据，不能代替外部信任根。真实 catalog 提供者尚未落地，测试 fixture 不能用作生产 catalog。
- 尚未执行真实 Tag、Release、VirusTotal 或 registry 收录的端到端验收；发布模块的测试使用本地 mock 和 fixture。
- 工具尚无 `tool-v*` 发行版；`bepack-release.json` 的 `tool.version` 使用 `source-<commit12>` 加源码清单摘要，不是伪造的二进制发行地址。
- Release 的不可变保护、通知 App、扫描账户配额都需要仓库管理员/官方基础设施配合，不能只靠模板文本保证。
